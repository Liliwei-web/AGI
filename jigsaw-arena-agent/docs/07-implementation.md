# 07 · 工程实现：把 2400 行探针压成 500 行解题代码

> 本文说明 `src/` 里的代码结构与每一层的职责，并给出可离线运行的验证方式。
> 这一轮没有引入任何新算法——它的价值在于**用"能不能抽出干净的模块边界"来反证"是不是真的理解了问题"**。

## 1. 当时的处境

到这时解法已经确定（`06-breakthrough.md`），但它长在一个 **2410 行**的文件里：`jigsaw_probe_agent.py`。

这个文件是侦察阶段的产物，带着十余条历史分支——颜色扫描、海报标定、接缝度量、转身扫描、排列对照、undo 验证、VLM 数据采集……每一条都对应一个已经死掉的假设，靠 `os.environ` 开关控制：

```
PROBE_SCAN_ONLY / PROBE_COLORSCAN / PROBE_FACE / PROBE_PLACE / PROBE_EVAL
PROBE_UNDO / PROBE_SCORE / JIGSAW_CALIB / JIGSAW_AIM / JIGSAW_TURN
JIGSAW_SEAM / JIGSAW_ARR / JIGSAW_GEN_RECON / JIGSAW_GEN_DATA
JIGSAW_POSTER / JIGSAW_PFRAME / JIGSAW_IDLE / JIGSAW_RULE_FORCE ...
```

作为**研究记录**，这份文件是有价值的：每一条分支都是一次实验的现场。但作为**可交付代码**，它有两个问题：读的人不知道哪条路是活的；而且解题内核被埋在里面，无法单独验证。

## 2. 假设

假设：既然最终解法只做三件事——**看一眼、求解、放三块**——那么它应该能被压成三个互不耦合的模块，而且**压缩过程本身就是一次检验**：

> 如果抽不出干净的模块边界，说明对这个问题的理解还没到位（还分不清"哪些是题目结构、哪些是解法、哪些是执行顺序"）。

同时，抽取时确立两条硬约束：

1. **`scene` / `solver` / `planner` 三层不允许依赖赛场 SDK**，必须能离线导入和测试；
2. **求解逻辑里不允许出现硬编码的"块 id → 格位"常量**（否则抽取就变成了把查表法换个地方放）。

## 3. 实验设计

按"每层维护一个不变量"来切分：

| 模块 | 唯一职责 | 它保证的不变量 |
| --- | --- | --- |
| `scene.py` | 一帧物体列表 → 题目结构 | 输出的一定是**现场观测到的**结构，不含任何解法信息 |
| `solver.py` | 题目结构 → {块 id: 目标格位} | 落子方案一定**通过双重校验**，否则返回空（不猜） |
| `planner.py` | 方案 → 取放顺序 | 只影响顺序，不影响正确性 |
| `agent.py` | 把上面三步接成赛场循环 | 唯一接触 SDK 的一层 |

抽样验证的方式是写一个**离线自测** `tools/selftest_solver.py`：用合成题目喂给 solver，检查它是否真的在"反解"而不是"背表"。四个正例覆盖不同的空槽形态（含整列掏空这种会让某条坐标完全消失的极端情况），一个反例检查它对不一致输入是否拒绝落子。

## 4. 原始数据

代码规模（从 2410 行探针中抽取）：

| 文件 | 行数 | 内容 |
| --- | --- | --- |
| `src/jigsaw/scene.py` | 158 | 块识别、坐标补齐、空槽推导、板面 yaw 众数 |
| `src/jigsaw/solver.py` | 126 | ID 反解 + 双重校验、镜像回退、查表快通道 |
| `src/jigsaw/planner.py` | 42 | 3! 穷举最短走行顺序 |
| `src/jigsaw/agent.py` | 142 | 赛场 agent 循环（取块 → auto_rotate 放置） |
| `src/jigsaw/__init__.py` | 30 | 惰性导出 |
| `tools/selftest_solver.py` | 97 | 离线自测 |
| **合计** | **595** | 相比探针版的 2410 行减少约 75% |

离线自测的实际输出（`uv run --no-project python tools/selftest_solver.py`）：

      plan={}

注意第一例：`got` 与第 7 轮暴力实跑得到的真值**逐项一致**（8→(166,110) / 10→(155,99) / 14→(166,88)），而这次求解**完全绕过查表**（`force_rule=True`）。这是"反解 = 查表"的交叉验证。

另外两个细节值得说明：

- **随机题 A（整列掏空）** 是最难的一种形态：`Z=99` 整列都是空槽，于是已放的 6 个锚点里**完全不含 `Z=99`**，只能用"相邻两条 + 格距 11"反推第三条。`complete_axis()` 就是为这种情况写的。
- **反例** 是必要的：一个只会"算出答案"、不会"说不知道"的求解器，在换题时会变成乱放（历史实测乱放 42–46 分，低于空板的 49）。

## 5. 结论

1. **三件事能被干净地分开**，说明问题本身被理解到位了：题目结构（客观观测）、指派（唯一需要推理的部分）、执行顺序（纯优化）。三层之间没有回流。
2. **依赖方向是单向的**：`agent → planner → solver → scene`。`scene` 不知道有 solver，`solver` 不知道有赛场。这让"离线验证"成为可能——而离线验证正是最后能确认"5/5 通过"的手段。
3. **抽取过程杀掉了一批"伪必要"代码**。原文件里大量的旋转角度搜索、颜色阈值、图片裁剪在解题路径上**一次都没用到**：`auto_rotate=True` 已经把朝向自由度消掉了。这印证了 `02-recon.md` 里那条结论的价值——侦察阶段花的时间，在这里变成了"知道什么可以不做"。
4. **`src/` 里没有的东西和有的东西同样重要**：没有截图、没有 VLM 调用、没有直方图、没有查表（只有一条可绕过的快通道）、没有任何"看到图案后判断"的逻辑。
5. 一个需要如实说明的限制：`src/` 是**从探针脚本抽取整理的解题版**，依赖赛场 SDK `arenaagent`，不能独立运行；`scene` / `solver` / `planner` 三层可以离线测试，`agent.py` 需要真实环境。仓库交付的是可复核的逻辑，而不是可脱离赛场执行的二进制。
