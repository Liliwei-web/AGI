# 04 · 第一代解法：查表（背题）

> 本文记录第 8 轮迭代。真值已经在手，这一轮要做的是"把真值变成能拿到 100 分的程序"。
> 这是整个项目里**最成功也最危险**的一步。

## 1. 当时的处境

上一轮（`03-brute-force-truth.md`）用暴力实跑拿到了真值：

```
8 → (166,110)   10 → (155,99)   14 → (166,88)
```

并且知道 `auto_rotate=True` 可以让 100 分成立。此时距离"能交一版"只差把它写成代码。

## 2. 假设

这一轮依赖一个**没有被验证过、但看起来完全合理**的前提：

> 本地 `train` 环境每次只出同一道题。

支持它的观察有三条：

- 多次重放静态题，块 id 与空槽位置完全一致（只有板面朝向 `target_yaw` 每局在变）；
- 题目签名的三要素（空槽形态、已放 6 块位置、待放 3 块 id）逐次相同；
- 6 种排列的实跑分数可复现（92 / 78 / 71 / 46 三次复跑一致）。

如果这个前提成立，那么"真值常量"就是这道题的完整解。

## 3. 实验设计

在 `_build_solve_spec()` 里写一张常量表，并**加一道模式守卫**：

```python
known_pattern = {(155.0, 99.0), (166.0, 88.0), (166.0, 110.0)}
pattern = {(round(s[0], 1), round(s[1], 1)) for s in self._empty_slots}
table = {}
if pattern == known_pattern:
    table = {"8": (166.0, 110.0), "10": (155.0, 99.0), "14": (166.0, 88.0)}
```

执行时以 `auto_rotate=True` 逐个放置三块。守卫的理由是：**空槽形态不同说明换题了，这时候查表没有意义**——与其猜，不如留空板（49 分）而不是吃错放惩罚（42 分）。

验证方式：反复跑 `train`，看 `jigsaw_score` 与总分是否稳定。

## 5. 结论

1. **查表法在本地是稳定满分的**，三次复跑完全一致，这是项目里第一个"能交付"的状态。
2. **但它只是"背题"，不是"解题"。** 它的正确性完全建立在"本地只出一道题"这个前提上——而这个前提从来没有任何证据支持，只是没有遇到反例。
3. 那道**模式守卫**无意中变成了最重要的设计。它让"背错题"不至于变成"乱放"：换题时不会因为表不匹配而把块扔到错误槽位。
4. 顺带确认了一个反直觉的事实：**满分也拿不到总分 100**。两个满分局（38.6s）总分都只有 98.83——说明评分里除了完成度还有时间项，这一条到 `08-performance.md` 才被量化。

### 这张表今天还在代码里

需要说明的是，这张常量表**至今仍然保留在 `_build_solve_spec()` 里**，作为已知空槽形态的一条快速通道：

```python
if pattern == known_pattern and not force_rule:
    table = {"8": (166.0, 110.0), "10": (155.0, 99.0), "14": (166.0, 88.0)}
```

保留它的理由不是"它还对"，而是它与第三代解法（`_solve_by_id_map()`，见 `06-breakthrough.md`）**对同一道题给出完全相同的答案**——两者互为交叉验证。真正决定泛化能力的是第三代；这张表只是一个可选的短路分支，并且可以被 `JIGSAW_RULE_FORCE=1` 强制绕过，用于验证"不查表也能对"。

## 6. 下一步

本地永远满分，意味着**在本地再也看不出对错**。要判断这张表是不是真解法，唯一的办法是让它去接触随机题。

而随机题只在正式 `test` 模式出现——于是问题变成了：随机题上，除了背下来的这道题以外的那些题，答案从哪里来？见 `05-falsified-hypotheses.md`。
